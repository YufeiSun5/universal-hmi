# KP 浏览器直接请求 v54

用户本机 KP 通过 `/httprequest` POST 返回 HTTP400，响应错误码为 `DEPTH_ZERO_SELF_SIGNED_CERT`。原厂 `httpRequestExec` 会由 KP 后台代理请求，使用 KP 后台自身的证书信任和网络路径。浏览器成功下载监控 helper，并不能证明这个后台代理也信任监控证书。错误回传不含本项目需要保存的用户令牌或 Cookie，本记录不收录它们。

## 修订

- `app/web/kp_bridge.js` v3 使用浏览器 `fetch` 直接调用监控 `/api/v1/kp/`，不调用 KP `/httprequest`。请求携带浏览器凭据以保留设备TLS身份，独立KP证明或联调授权仍在POST正文中，不加到URL或KP认证头；8秒超时取消，禁止重定向及缓存。
- `server/kp.go` 仅向已经配置且精确匹配的KP来源提供允许凭据的CORS，公网设备/IP准入及业务只读不变；不关闭TLS验证，不自动导入未知证书。
- 配置页生成脚本检查helper版本3，避免已加载v2后继续调用旧实现。失败页分别显示请求超时、网络/CORS错误及响应解析错误；联调授权失效不再只要求登录KP。

此前v53隔离替身以浏览器fetch实现同名httpRequestExec，没有覆盖原厂后台代理链路。因此v53本地模拟通过不能代表本机KP连接远端已通过。新浏览器测试将旧代理方法设为明确失败，验证它完全未被调用。

## 升级操作

升级远端监控服务器到v54，保留原工程和接入配置。在监控开发态“登录与安全→KP接入”确认联调模式、原固定测试账号及KP来源 `http://127.0.0.1:11005`；后台核验地址继续留空。重新读取配置，复制最新“画面打开时”脚本替换KP承载画面的“连接→打开时”，关闭事件保持生成的close脚本。刷新整个KP运行页后重开画面，新的请求应直接访问监控服务器 `/api/v1/kp/bootstrap`，不再经KP `/httprequest`。

如果仍失败，只提供请求状态及脱敏响应正文。浏览器自己的HTTPS信任、设备证书/IP准入和正确KP来源仍必须满足；不要设置跳过证书验证。其他KP功能仍可能使用其自身/httprequest，不以页面上任何同名请求都必须消失作为验收。
